## 패턴

JIT 검색은 보통 **새 위키 entry 생성 전 중복 확인** 목적으로 프레이밍된다. 그러나 더 넓게 보면 **작업 예방 게이트**로 작동한다 — 기존 해결책이 존재하면 재분석을 단락시킨다.

```
표준 프레이밍: JIT search → "이 토픽 이미 있나?" → 없으면 새 entry 생성
예방 게이트 프레이밍: JIT search → "이 작업 이미 해결됐나?" → 해결됐으면 작업 skip
```

## cycle 1390 증거

moneyball CI 실패 60건 triage 과정에서 JIT search 2회가 결정을 변경했다.

### 케이스 1: batch-close vs 개별 분석

```
JIT query: "moneyball CI 실패 ws vite 취약점"
hit score: 0.89 (TODOS counter pattern entry)
결정 변경: 60건 개별 원인 분석 → 배치 close + TODOS 카운터 갱신
절감: ~59 × 개별 분석 비용 ≈ 수십 분
```

### 케이스 2: Claude CLI auth 신규 분석 방지

```
JIT query: "claude cli 인증 실패 blog-autopilot healthcheck"
hit score: 0.91 (claude-max-subscription-github-actions-self-hosted-runner-pattern)
결정 변경: 새 root cause 분석 → 기존 wiki entry + runbook 참조
절감: 1 root cause analysis + 1 솔루션 작성 비용
```

## 비용 구조

| 항목 | 비용 |
|---|---|
| JIT search 1회 | ~3-5초 (embedding lookup) |
| 개별 incident 분석 1건 | ~2-5분 |
| 60건 개별 분석 vs 1회 search + batch | 60× 비용 차이 |

비대칭성: 검색 1회 비용 ≪ 방지된 분석 비용. JIT search threshold(0.85)를 넘는 hit가 1건만 나와도 ROI 양수.

## 결정 변경 유형

JIT search hit가 나왔을 때 가능한 결정 변경:

| 원래 계획 | hit 내용 | 변경된 행동 |
|---|---|---|
| 개별 incident 분석 | 기존 TODOS 추적 항목 | batch-close + 카운터 갱신 |
| 새 솔루션 분석 작성 | 기존 wiki entry/solution | 참조 링크만 추가 |
| 새 entry 생성 | 기존 유사 entry | connection 추가 or skip |
| fix-incident chain | 기존 known fix | 동일 fix 재적용 (탐색 없이) |

## 작업 예방 게이트 vs 토픽 발견 마찰

| 측면 | 토픽 발견 마찰 (기존 패턴) | 작업 예방 게이트 (이 패턴) |
|---|---|---|
| 목적 | 신규 entry 토픽 찾기 | 기존 해결책 재발견 |
| hit 결과 | "이미 있다 → 다른 토픽 찾아야" | "이미 해결됐다 → 작업 skip" |
| 마찰 방향 | 마찰 증가 = 성숙 신호 | 마찰 감소 = 절약 신호 |
| 사용 chain | explore-idea | worker-incident-triage, fix-incident |

## 실용 원칙

**작업량 비례 원칙**: 처리 비용이 클수록 JIT search 먼저. 60건 batch-close는 JIT search 없이 하면 수십 분 낭비. 1건 trivial fix는 JIT 없이 직접 처리.

**결정 변경 가시화**: JIT hit로 결정이 바뀌었으면 cycle_state.execution.results에 "JIT search 결정 변경: (변경 내용)" 명시. 측정 가능한 ROI evidence 축적.

**false negative 주의**: score=0.84 (threshold 미달) = "없다고 확정" 아님. 고비용 작업이면 threshold 하향 조정 또는 쿼리 재작성으로 재검색.
