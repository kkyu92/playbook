위키 엔트리 수가 증가할수록, 신규 엔트리의 가치는 선형이 아닌 복리적으로 증가한다.

## 메커니즘

### 1. 연결 밀도 증가

신규 엔트리가 참조할 수 있는 기존 엔트리 수 = N (현재 위키 크기).
- 엔트리 100개 위키: 신규 엔트리가 참조 가능한 엔트리 최대 100개
- 엔트리 400개 위키: 신규 엔트리가 참조 가능한 엔트리 최대 400개

실제 connections는 3-5개 수준이지만, 적절한 연결을 찾을 확률이 높아진다.

### 2. JIT 검색 정밀도

JIT 검색(의미 기반)은 index 크기에 비례해 정확한 매칭을 찾을 가능성이 높아진다:

```
엔트리 100개 → 쿼리당 평균 0.5개 threshold 통과
엔트리 400개 → 쿼리당 평균 2-3개 threshold 통과
```

더 많은 기존 엔트리 = 중복 엔트리 방지 정확도↑, 연결 후보 발견↑, 맥락 공유↑.

### 3. 클러스터 형성

관련 엔트리가 누적되면 클러스터가 형성되어 새 엔트리가 단독으로 문서화할 수 없는 패턴을 클러스터 내 다른 엔트리와 함께 설명 가능.

## 사례 — cycle 1370 incident 클러스터 (entries #317-#323)

```
#317 — 기존 연결 2개 (첫 엔트리, 연결 대상 적음)
#318 — 기존 연결 2개 + #317 참조 (= 3개)
#319 — 기존 연결 2개 + #317,#318 참조 (= 4개)
#320 — 기존 연결 1개 + #317,#318,#319 참조 (= 4개 — 클러스터 통합)
#321 — 기존 연결 3개 (독립적이지만 클러스터 지식 활용)
#322 — 기존 연결 3개 + #321 참조 (= 4개)
#323 — 기존 연결 1개 + #317,#322 참조 (= 3개 — meta-synthesis)
```

클러스터 후기 엔트리(#320, #323)는 선행 클러스터 엔트리를 references로 사용해 더 깊은 맥락을 제공. 단독으로 쓰면 길어질 설명이 참조로 대체됨 → 각 엔트리가 핵심 내용에 집중 가능.

## 복리 가치 vs 단순 누적

**단순 누적** (선형): N개 엔트리 = N개 독립 패턴. 연결 없음.

**복리 가치** (지수): N개 연결 엔트리 = N + N*(N-1)/2 개 연결 가능.

실제로는 연결이 선택적이라 지수적이지 않지만, 클러스터 내부 연결이 주는 가치는 명확:
- 독자가 하나의 엔트리에서 시작해 클러스터 전체를 탐색 가능
- 각 엔트리가 다른 엔트리의 맥락을 제공
- 중복 설명 없이 점진적 세부화 가능

## 실용적 함의

### 엔트리 작성 전략

1. **standalone 엔트리 우선**: 처음에는 독립적 가치가 있는 엔트리 작성
2. **클러스터 감지**: 관련 엔트리 2-3개 쌓이면 클러스터 형성 인식
3. **클러스터 통합 엔트리**: SOP/framework 엔트리로 클러스터 통합 (#320이 #317-#319를 통합한 것처럼)
4. **cross-cluster 연결**: 다른 클러스터의 관련 엔트리 참조로 도메인 간 연결

### JIT 검색 활용도 향상

엔트리 증가 → JIT 검색 효율 향상 → 신규 엔트리 작성 시 중복 방지와 연결 발견이 쉬워짐 → 더 정확한 엔트리 작성 → 위키 품질 향상 → JIT 검색 효율 또 향상 (선순환).

### 임계점

경험적으로:
- **< 50 entries**: 클러스터 형성 어려움, JIT 검색 자주 "No match"
- **50-200 entries**: 주요 도메인 클러스터 형성 시작
- **200+ entries**: 도메인 간 연결 자연 발생, JIT 정밀도 안정화
- **400+ entries**: 메타 패턴(SOP, framework) 작성 자연스러워짐

현재 허브: 404 entries → 메타 패턴 작성 단계 진입.
