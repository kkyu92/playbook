배치 세션(N=20+ 사이클)에서 wiki entry를 여러 개 추가할 때, 해당 session 내에서 JIT 검색(`pnpm search`)이 새로 추가한 entry를 반환하지 못하는 현상.

## 원인

`public/embeddings.json` 은 `.gitignore`에 등록된 로컬 전용 파일. `pnpm embed-content`를 명시적으로 실행하지 않으면 새 entry가 embeddings에 포함되지 않음.

```
explore-idea 사이클: entry #293 추가 → content/infrastructure/*.mdx 생성
                      ↓
JIT 검색 (다음 사이클): pnpm search "Claude rate limit" → "no match"
                      ↓
이유: embeddings.json이 entry #293 추가 이전 상태 (2729 chunks → 2741 chunks 미반영)
```

## 감지 방법

```bash
# embeddings.json 의 chunk 수 확인
python3 -c "import json; d=json.load(open('public/embeddings.json')); print(len(d.get('chunks',[])))"
# 출력: 2729

# 실제 entry 수 (generate-content-manifest 기준)
node scripts/generate-content-manifest.mjs 2>&1 | grep "entries"
# 출력: 378 entries

# 신규 entry가 embeddings에 있는지 확인
python3 -c "
import json
d = json.load(open('public/embeddings.json'))
found = [c for c in d.get('chunks',[]) if '<new-slug>' in c.get('slug','')]
print(len(found), 'chunks for new entry')
"
```

## 갱신 판단 기준

| 상황 | embed-content 실행 여부 |
|------|------------------------|
| 배치 세션 중간에 JIT 검색이 신규 entry를 찾아야 할 때 | 실행 (156초 소요) |
| 신규 entry의 connections 중복 확인이 필요할 때 | 실행 |
| 배치 세션 마무리 전 최종 상태 정합 | 실행 |
| 배치 세션이 끝나고 다음 세션에서만 사용할 때 | 다음 세션 시작 시 실행 |
| BRANCHED 상태여서 origin 기준으로만 검색해도 될 때 | skip 가능 |

## 비용 트레이드오프

- 전체 재생성: 2741 chunks × 0.057s/chunk ≈ 156초
- 신규 entry 평균 chunk 수: ~7개 (entry 1개 기준)
- 현재 구현: 전체 재생성 (incremental X) — [P3] TODOS 항목

## 배치 세션 실무 패턴

```bash
# 배치 중 여러 entry 추가 후 1회 일괄 갱신 (가성비 ↑)
# entry 추가할 때마다 embed X — 마지막에 한 번

# 중간 추가분이 즉시 검색에 필요하다면:
pnpm embed-content  # 기다림

# 아니면 배치 끝 후:
pnpm embed-content  # 다음 세션 시작 전
```
