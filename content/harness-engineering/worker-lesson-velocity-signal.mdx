## 문제

허브가 워커의 활동 수준을 파악하려면 워커 레포 직접 접근, issue 목록 조회, git log 스캔이 필요했다. GH Actions `auto-ingest.yml` (worker-lesson dispatch 수신) 로그는 허브 레포 안에 있지만, 이 로그에서 "지금 워커가 얼마나 활발히 개발 중인가?"를 읽는 관행이 없었다.

결과: 워커가 hot development phase인지, stable 상태인지, dormant인지를 허브 진단 단계에서 즉시 알 수 없었다.

## 패턴

`worker-lesson` repository_dispatch 발화 속도 = **Pull(b) 학습 속도 신호**.

워커 LLM 세션이 lesson을 생성하면 `submit-lesson.yml` → `auto-ingest.yml` 체인으로 허브에 arrive한다. 이 arrive 속도를 rolling window로 측정:

```bash
# 최근 2시간 worker-lesson fires 계산
gh run list \
  --workflow=auto-ingest.yml \
  --created "$(date -u -v-2H +%Y-%m-%dT%H:%M:%SZ)" \
  --json createdAt \
  --jq 'length'
```

### 3단계 분류

| Phase | Rate | 해석 |
|---|---|---|
| **Burst** | ≥5 fires/hour | 워커 hot development — 빠른 사이클 반복, 많은 lesson 누적 |
| **Drizzle** | 1–4 fires/hour | 워커 steady maintenance — 정기 개선, 안정적 진행 |
| **Zero** | 0 fires/2h+ | 워커 stable/dormant — 정상 휴식 또는 비활성 전환 |

## 각 단계의 의미

**Burst**: 워커가 N회 연속 사이클을 고속 회전 중. 허브 입장에서는 Pull(b) 축 throughput 최대화 구간. 이 lesson들이 빠르게 쌓이므로 worker-incident-triage chain 필요 여부도 함께 확인.

**Drizzle**: 정상 maintenance 패턴. 특별한 조치 불필요.

**Zero**: 두 가지 해석이 공존:
- (양호) 워커가 stable phase — lesson 생성 할 이벤트 없음 = 건강한 전문화
- (주의) 워커 dormancy가 예상보다 길어진 경우 → 허브 `worker-incident-triage` chain 검토

`fix-incident dormancy = 건강한 전문화` 원칙(hub cycle 818 evidence)과 동일 논리: Zero 자체가 문제가 아님. 맥락이 판단 기준.

## 실전 측정법

허브 진단 단계 (develop-cycle-hub 사이클 단계 1) 에서:

```bash
# 최근 2시간 window
FIRES=$(gh run list \
  --workflow=auto-ingest.yml \
  --repo kkyu92/playbook \
  --json createdAt,status \
  --jq '[.[] | select(.status == "completed")] | length')

WINDOW_H=2
RATE=$(echo "scale=1; $FIRES / $WINDOW_H" | bc)

if [ $(echo "$RATE >= 5" | bc) -eq 1 ]; then
  echo "BURST — 워커 hot development ($RATE fires/h)"
elif [ "$FIRES" -gt 0 ]; then
  echo "DRIZZLE — 워커 steady maintenance ($RATE fires/h)"
else
  echo "ZERO — 워커 stable/dormant (0 fires in ${WINDOW_H}h)"
fi
```

진단 key_findings에 phase 박제 → chain 선택 힌트로 활용. Burst 시 `worker-incident-triage` 우선 확인, Zero 시 `closed-loop-design` 또는 다른 source 집중.

## 실전 증거

**2026-05-19 moneyball 세션**:
```
08:51 worker-lesson fire
08:52 worker-lesson fire  (+1min)
08:56 worker-lesson fire  (+4min)
08:57 worker-lesson fire  (+1min)
09:29 worker-lesson fire  (+32min)
09:30 worker-lesson fire  (+1min)
09:32 worker-lesson fire  (+2min)
09:39 worker-lesson fire  (+7min)
```
48분 window 8 fires ≈ 10 fires/hour → **Burst phase 확인**.

같은 날 허브 진단에서 이 패턴 포착 → "worker-lesson burst = moneyball hot dev" 즉시 추론 성공. 워커 레포 직접 접근 불필요.

## 한계

- **Quality vs Quantity**: lesson 생성 속도 ≠ lesson 질. Burst = 많은 lesson이지 좋은 lesson이 아님. 개별 lesson confidence는 별도 평가 필요.
- **Burst 원인 모호성**: burst가 정상 고속 개발인지, 반복 실패로 인한 debug commit 누적인지 fire 수만으로 구분 불가. 병행 확인: `gh run list --workflow=ci.yml --repo <worker-repo>` CI 실패 여부.
- **한 워커 측정**: 복수 워커 환경에서는 `auto-ingest.yml` log가 워커별 구분 없이 집계됨. 워커별 velocity는 lesson commit body의 worker name 필드로 필터.

## 연결 패턴

이 패턴은 [hub-worker-compounding-pattern](hub-worker-compounding-pattern)의 Pull(b) 축 (워커→허브 자동 학습 흐름)을 **관측 가능**하게 만드는 도구다. 흐름이 존재하는 것과 흐름의 속도를 아는 것은 다르다.

[agentic-chain-saturation-detection](agentic-chain-saturation-detection) 과 대칭: chain saturation은 "같은 chain이 너무 자주 발화하는가?"를 감지하는 반면, lesson velocity는 "워커가 허브에 데이터를 얼마나 빠르게 보내는가?"를 감지한다. 둘 다 rate-based observability 패턴.
