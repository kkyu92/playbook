최근 UIUC, Meta, Stanford의 공동 연구에서 제시된 'Code as Agent Harness' 개념은 인공지능 에이전트 설계에 있어 코드의 역할을 재정의합니다. 기존에는 LLM이 코드를 생성하는 결과물로 여겨졌다면, 이제 코드는 에이전트가 추론하고, 행동하고, 상태를 저장하며, 피드백을 검증하는 핵심적인 '실행 기반(operational substrate)'으로 자리매김합니다. 이 변화는 더욱 견고하고 신뢰할 수 있는 에이전트 시스템을 구축하기 위한 하네스 설계 원칙 강화의 필요성을 강조합니다. 본 엔트리에서는 이러한 관점을 바탕으로 에이전트 하네스 설계의 핵심 원칙들을 다룹니다.

## 핵심 설계 원칙

### 1. 실행 환경 격리 및 보안 (Execution Environment Isolation & Security)
에이전트가 생성한 코드는 잠재적으로 불안정하거나 악의적인 내용을 포함할 수 있으므로, 안전하고 격리된 환경에서 실행되어야 합니다. 이는 샌드박싱(sandboxing), 컨테이너화(containerization, 예: Docker), 또는 가상화(virtualization) 기술을 활용하여 구현됩니다. 코드 실행 시 발생할 수 있는 시스템 오작동이나 데이터 유출을 방지하는 것이 최우선입니다.

### 2. 명확한 인터페이스와 확장성 (Clear Interfaces & Extensibility)
에이전트 하네스는 에이전트와 외부 도구 및 환경 간의 명확하고 일관된 인터페이스를 제공해야 합니다. 이를 통해 에이전트는 필요한 도구를 쉽게 호출하고, 그 결과를 파싱하여 다음 추론에 활용할 수 있습니다. 또한, 새로운 도구나 API가 추가될 때 하네스를 유연하게 확장할 수 있도록 플러그인(plugin) 방식이나 모듈러(modular) 아키텍처를 채택하는 것이 중요합니다.

### 3. 상태 관리 및 지속성 (State Management & Persistence)
에이전트의 실행은 단일 요청으로 끝나지 않고 여러 단계에 걸쳐 이루어지는 경우가 많습니다. 하네스는 에이전트의 중간 상태, 실행 로그, 생성된 아티팩트(artifacts) 등을 효율적으로 관리하고 지속(persist)할 수 있어야 합니다. 이는 장기적인 태스크 수행, 실패 복구, 그리고 디버깅에 필수적입니다. 키-밸류 스토어, 데이터베이스, 또는 분산 캐시 시스템을 활용할 수 있습니다.

### 4. 피드백 루프와 자율 검증 (Feedback Loops & Autonomous Validation)
코드를 실행 기반으로 활용하는 핵심 이유 중 하나는 에이전트가 자신의 행동 결과를 직접 관찰하고 평가하여 다음 추론에 반영하는 피드백 루프를 구축하는 것입니다. 하네스는 코드 실행 결과(stdout, stderr, exit code)를 캡처하고, 이를 정규 표현식, 스키마 검증, 또는 다른 LLM 기반의 검증 에이전트를 통해 분석하여 에이전트에게 피드백을 제공하는 메커니즘을 내장해야 합니다. 이는 에이전트의 자율적인 자가 수정(self-correction) 능력을 강화합니다.

### 5. 관측 가능성 및 디버깅 (Observability & Debugging)
복잡한 에이전트 시스템에서는 어떤 코드가 언제, 어떻게 실행되었는지 파악하기 어렵습니다. 하네스는 코드 실행 과정, 에이전트의 중간 추론 단계, 상태 변화 등을 상세하게 로깅(logging)하고 모니터링(monitoring)할 수 있는 기능을 제공해야 합니다. 이를 통해 문제 발생 시 원인을 빠르게 진단하고 에이전트의 행동을 이해할 수 있습니다.

## 코드 기반 하네스 아키텍처

아래 Mermaid 다이어그램은 코드 기반 에이전트 하네스의 일반적인 흐름을 보여줍니다. 에이전트의 '계획(Plan)' 단계에서 코드가 생성되면, 하네스는 이 코드를 '실행(Execute)'하고 그 결과를 '관찰(Observe)'하며 '검증(Validate)'하여 다시 에이전트의 '반영(Reflect)' 단계로 전달합니다.

```mermaid
graph TD
    A[에이전트] --> B{계획/코드 생성}
    B --> C[코드 하네스]
    C --> D{코드 실행 (샌드박스)}
    D --> E["실행 결과 (Stdout/Stderr)"]
    E --> F{피드백 검증 모듈}
    F --> G[상태 관리]
    F -- 성공 --> A
    F -- 실패 --> H[에이전트 : 자가 수정]
    H --> B
    G --> D

    subgraph "코드 하네스 아키텍처"
        C --> C1[인터페이스 레이어]
        C1 --> C2["실행 엔진 (Sandbox)"]
        C2 --> C3[상태 저장소]
        C3 --> C4[검증/피드백 시스템]
        C4 --> C5[로깅/모니터링]
    end
```

## 실제 코드 예제

다음은 Python을 이용한 간단한 코드 실행 및 결과 캡처 하네스 구성 예시입니다. 이 예제는 에이전트가 생성한 Python 코드를 안전하게 실행하고, 그 출력과 오류를 캡처하는 기본 구조를 보여줍니다.

```python
import subprocess
import json
import os

class AgentCodeHarness:
    def __init__(self, sandbox_dir="./sandbox"): # Sandbox directory
        self.sandbox_dir = os.path.abspath(sandbox_dir)
        os.makedirs(self.sandbox_dir, exist_ok=True)

    def execute_python_code(self, code_content: str, timeout: int = 10) -> dict:
        """
        에이전트가 생성한 Python 코드를 샌드박스 환경에서 실행하고 결과를 반환합니다.
        """
        temp_file_path = os.path.join(self.sandbox_dir, "agent_script.py")
        result = {"stdout": "", "stderr": "", "exit_code": None, "error": None}

        try:
            with open(temp_file_path, "w", encoding="utf-8") as f:
                f.write(code_content)

            # Docker, gVisor, 또는 rbox 같은 실제 샌드박스 환경과 통합 필요
            # 여기서는 단순히 subprocess를 사용하지만, 실제 프로덕션에서는 강력한 격리 필요
            process = subprocess.run(
                ["python3", temp_file_path],
                capture_output=True,
                text=True,
                timeout=timeout,
                cwd=self.sandbox_dir # 실행 디렉토리 제한
            )

            result["stdout"] = process.stdout
            result["stderr"] = process.stderr
            result["exit_code"] = process.returncode

        except subprocess.TimeoutExpired:
            result["error"] = "Execution timed out."
            result["stderr"] = f"Execution timed out after {timeout} seconds."
        except Exception as e:
            result["error"] = f"Execution failed: {e}"
            result["stderr"] = str(e)
        finally:
            # 실행 후 임시 파일 정리 (선택 사항, 디버깅 시 유지 가능)
            if os.path.exists(temp_file_path):
                os.remove(temp_file_path)

        return result

    def validate_output(self, execution_result: dict, expected_pattern: str = None) -> bool:
        """
        실행 결과를 검증합니다. (간단한 패턴 매칭 예시)
        """
        if execution_result["exit_code"] != 0:
            print(f"Validation Failed: Non-zero exit code {execution_result["exit_code"]}")
            return False
        if execution_result["error"]:
            print(f"Validation Failed: {execution_result["error"]}")
            return False
        if expected_pattern and expected_pattern not in execution_result["stdout"]:
            print(f"Validation Failed: Expected pattern '{expected_pattern}' not found.")
            return False
        return True

# --- 사용 예시 ---
harness = AgentCodeHarness()

# 성공적인 코드
successful_code = """
print("Hello from agent!")
print("Data processed successfully.")
"""
success_res = harness.execute_python_code(successful_code)
print("Success Result:", success_res)
print("Validation Status:", harness.validate_output(success_res, "successfully"))

# 오류가 있는 코드
error_code = """
raise ValueError("Agent simulated error")
"""
error_res = harness.execute_python_code(error_code)
print("Error Result:", error_res)
print("Validation Status:", harness.validate_output(error_res))

# 시간 초과 코드
timeout_code = """
import time
time.sleep(15) # 15초 슬립
print("Should not be reached")
"""
timeout_res = harness.execute_python_code(timeout_code, timeout=5)
print("Timeout Result:", timeout_res)
print("Validation Status:", harness.validate_output(timeout_res))
```

이 예제는 `subprocess` 모듈을 사용하여 Python 코드를 실행하지만, 2026년 에이전트 엔지니어링에서는 Docker, gVisor, 또는 WASM(WebAssembly) 기반 런타임과 같은 더 강력한 격리 메커니즘을 통합하여 보안과 리소스 제어를 강화하는 것이 일반적입니다. 특히 `cwd` (Current Working Directory)를 제한하는 것은 코드의 접근 범위를 좁히는 중요한 보안 조치입니다.

## 트레이드오프

에이전트 하네스 설계 원칙을 강화할 때 고려해야 할 주요 트레이드오프는 다음과 같습니다.

*   **유연성 vs. 보안**: 매우 유연하게 어떤 코드든 실행할 수 있는 하네스는 잠재적인 보안 위험을 높입니다. 반면, 엄격한 샌드박싱과 코드 검증은 에이전트의 자유로운 행동을 제약할 수 있습니다. 언제 좋고/언제 나쁜지: 프로토타이핑이나 내부 연구용으로는 유연성이 좋지만, 프로덕션 환경이나 외부 연동 시에는 강력한 보안이 필수적입니다.
*   **성능 오버헤드 vs. 관측 가능성/디버깅**: 상세한 로깅, 실시간 모니터링, 그리고 복잡한 검증 파이프라인은 시스템에 상당한 성능 오버헤드를 발생시킬 수 있습니다. 언제 좋고/언제 나쁜지: 초기 개발 및 디버깅 단계에서는 높은 관측 가능성이 중요하지만, 대규모 고성능 시스템에서는 최적화된 로깅 전략과 비동기 처리가 요구됩니다.
*   **개발 복잡성 vs. 에이전트 능력**: 정교하고 견고한 하네스를 구축하는 것은 상당한 엔지니어링 노력을 필요로 합니다. 이는 에이전트의 잠재적 능력 향상과 비례하지만, 초기 개발 속도를 늦출 수 있습니다. 언제 좋고/언제 나쁜지: 에이전트의 임무가 Critical하고 복잡할수록 초기 투자 가치가 높으며, 단순 반복 작업 에이전트에는 과도한 설계일 수 있습니다.
*   **일반성 vs. 도메인 특화**: 모든 종류의 에이전트 태스크에 적용할 수 있는 범용 하네스는 특정 도메인에 최적화된 하네스보다 성능이나 효율이 떨어질 수 있습니다. 언제 좋고/언제 나쁜지: 다양한 에이전트 모델과 태스크를 지원해야 하는 플랫폼에는 일반적인 하네스가 적합하고, 특정 산업이나 애플리케이션에 특화된 에이전트에는 도메인 전문 지식을 활용한 맞춤형 하네스가 유리합니다.
*   **자동화된 피드백 vs. 인간 개입**: 에이전트의 코드 실행 결과에 대한 완전 자동화된 피드백 및 자가 수정은 효율적이지만, 예상치 못한 상황에서 오류를 증폭시킬 수 있습니다. 중요한 결정이나 민감한 작업에는 인간의 검토 및 승인 단계가 필요합니다. 언제 좋고/언제 나쁜지: 반복적이고 저위험 작업에는 자동화된 피드백이 적합하며, 고위험 또는 창의적 태스크에는 인간의 루프(Human-in-the-Loop)가 필수적입니다.

## 실전 체크리스트

에이전트 하네스 설계를 강화할 때 다음 체크리스트를 활용하여 시스템의 견고성을 검증할 수 있습니다.

*   [ ] 모든 에이전트 생성 코드가 리소스(CPU, 메모리, 네트워크) 제한이 적용된 격리된 샌드박스 환경에서 실행되는가?
*   [ ] 코드 실행의 표준 출력(stdout), 표준 에러(stderr), 종료 코드(exit code)가 명확하게 캡처되어 에이전트 피드백 루프에 활용되는가?
*   [ ] 에이전트의 중간 상태와 실행 아티팩트가 영구적으로 저장되고, 재시작 시 복구 가능한가?
*   [ ] 에이전트가 실행하는 외부 도구 호출에 대한 접근 제어(ACL) 및 인가(authorization) 메커니즘이 구현되어 있는가?
*   [ ] 코드 실행 전, 에이전트가 생성한 코드에 대한 정적 분석(코드 스타일, 잠재적 보안 취약점) 또는 동적 테스트가 자동으로 수행되는가?
*   [ ] 하네스 내에서 발생한 모든 코드 실행 이벤트(시작, 종료, 오류, 결과)가 중앙 집중식 로깅 시스템으로 전송되어 모니터링 가능한가?
*   [ ] 중요하거나 고위험군 태스크의 경우, 에이전트의 코드 실행 결과를 인간이 검토하고 승인할 수 있는 워크플로우가 통합되어 있는가?
