## 문제

자율 에이전트 시스템에서 메타 체인(skill-evolution, expand-scope 등)의 발화 빈도를 어떻게 조절하는가?

- **너무 잦으면**: 비용 증가 + 잡음 (작업 맥락 없는 self-calibration)
- **너무 드물면**: 실제 phase 변화를 감지 못해 시스템 퇴화

직관적 해법은 "N 사이클마다 발화"(fixed-interval) 또는 "특정 이벤트 감지 시 발화"(event-driven). 그러나 둘 다 한계가 있다 — fixed-interval 은 phase 변화에 둔감, event-driven 은 조건 설계가 복잡하고 false-positive에 취약.

슬라이딩 윈도우 임계값 방식은 이 두 한계를 구조적으로 해결하며, 동시에 **예상치 못한 자연 oscillation**을 생성한다.

## 메커니즘

### 트리거 설계

```
[조건]: 직전 N 사이클 중 meta-chain 점유율 < threshold%
[윈도우]: N = 20 (슬라이딩, 최신 20 cycle JSON 기반)
[임계값]: 40%
[판단]: B = (SE_count / 20 < 0.40) → FAIL 시 마커 박제
```

Playbook hub develop-cycle에서 skill-evolution(SE) chain의 Trigger-5:
- 직전 20 사이클 중 SE 점유율 < 40% → B FAIL → 다음 사이클 SE 강제 발화

### Oscillation 생성 과정

```
[상태 1] SE 미발화 누적 → window rate 하락 → threshold 미만 (B FAIL)
        ↓
[트리거] 마커 박제 → 다음 사이클 SE 강제 발화
        ↓
[상태 2] SE 발화 → window에 SE 진입 → rate 상승 → threshold 초과 (B PASS)
        ↓
[skip]  마커 미박제 → 이후 N 사이클 skip
        ↓
[자연 하락] 과거 SE cycles가 window에서 이탈 → rate 재하락 → B FAIL 재도달
        ↓
[재트리거] → [상태 1]로 복귀
```

이 루프는 외부 개입 없이 자기강화적으로 유지된다. **oscillation 주기 = 윈도우 크기(N) × threshold비율** 에 의해 자연 결정된다.

### 수학적 구조

threshold 40%, window 20 기준:
- fire 직후: window 내 SE ≥ 8개 필요 (40%)
- skip 상태 유지 가능한 최대 비-SE 연속: SE 8개 모두 이탈하기까지 ≈ 8~12 사이클
- 실측 oscillation 주기: 평균 3~5 사이클 (skip 2~3회 후 재발화)

이 주기는 다른 active chain (curate/explore-idea) 발화 빈도에 따라 달라진다 — 비-SE 사이클이 많을수록 window에서 SE 이탈 속도가 빨라져 oscillation 가속.

## 감쇠(Damper) — Skip 조건 A+B

자연 oscillation 자체는 의도된 결과이지만, **과잉 발화** 방어를 위해 skip 조건이 감쇠로 작동한다:

| 조건 | 의미 | 감쇠 효과 |
|---|---|---|
| **A** | 직전 SE 대비 0회 chain 명단 동일 | phase 안정 확인 → 새 정보 없음 |
| **B** | 직전 20 사이클 SE 점유율 ≥ 40% | 이미 충분한 calibration |

A+B 모두 충족 시 → 마커 박제 skip → oscillation 자연 휴식.

```
명단 변화 감지 (phase 전환 신호) → A FAIL → 마커 강제 박제 → 다음 사이클 SE
명단 안정 + B PASS → skip → 자연 휴식 → window shift 후 B FAIL 재발화
```

이 구조는 **정보 이득이 없는 SE 발화를 자동 억제**한다.

## Fast-path 최적화

oscillation이 충분히 누적(n ≥ 5)되면 "stable oscillation" 확인 = SE chain의 heavy sequence 전체를 실행할 필요 없음:

```
fast-path 조건: 명단 동일(A PASS) + oscillation_n ≥ 5
fast-path 동작: MIGRATION-PATH append + TODOS update → retro-only (chain 나머지 skip)
```

Heavy sequence (office-hours → spec write → SKILL.md Edit → smoke → PR) 대비 90% 비용 절감. Stable oscillation = 시스템이 이미 올바르게 작동 중임을 의미하므로 변경 불필요.

## Phase 전환 신호

oscillation 명단 변화 = phase 전환 감지기로 활용 가능:

- **명단 확대** (chain 추가): 신규 도메인 비활성화 → project phase 수렴
- **명단 축소** (chain 이탈): 비활성 chain 재활성화 → 새 도메인 도전

자동 calibration 없이는 "어떤 chain이 현재 project에서 자연 불활성인가"를 추적하기 어렵다. Trigger-5 + 명단 추적이 이를 구조적으로 제공한다.

## 설계 가이드

이 패턴이 적합한 조건:

1. **메타 체인이 존재**: 시스템 자체를 calibrate하는 체인 (skill-evolution, retrospective 등)
2. **발화 빈도가 고정되면 안 됨**: project phase에 따라 필요 빈도가 변함
3. **비용이 asymmetric**: 메타 체인 발화 비용 >> 일반 체인 발화 비용
4. **window size ≥ 10**: 통계적 안정성. 작으면 noise 민감 (N=5는 과잉 반응)

파라미터 선택:
- `N (window size)`: 더 클수록 oscillation 주기 길어짐 (안정적, 둔감)
- `threshold`: 낮을수록 발화 빈도 높아짐. 40%는 "5사이클 중 2회" 수준
- `oscillation_n`: fast-path 판정 기준. 5회 이상 = "패턴 확립" 충분 근거

## 주의 — watch.sh kill의 영향

batch 시스템에서 timeout kill이 chain_selected를 미박제할 경우 JSON 기반 rate 계산에 undercount 발생:

```
cycle 569 evidence: watch.sh kill → 568.json chain='unknown' → window SE rate 35%→30% 감소
→ 실제 40%지만 JSON=35% → B FAIL 지속 → 추가 SE 발화 (cycle 569/570)
→ window shift 후 자연 흡수 (3사이클 내)
```

Kill event는 oscillation을 일시 가속시키지만, window가 충분히 크면(N=20) 자연 흡수됨. 근본 해결보다 "허용 범위 내 잡음"으로 분류.
