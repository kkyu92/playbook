대규모 언어 모델(LLM) 기반 애플리케이션이 프로덕션 환경에서 핵심 역할을 수행함에 따라, LLM API 호출의 안정성을 확보하는 것이 중요해졌습니다. LLM API는 네트워크 지연, 서비스 과부하, 임시 오류 등 다양한 원인으로 인해 실패할 수 있습니다. 이러한 불안정성은 사용자 경험 저하, 비용 증가, 서비스 중단으로 이어질 수 있습니다. 본 문서는 LLM API 호출의 안정성을 위한 핵심 폴리시(Policy)와 재시도(Retry) 로직 구현 방안을 제시합니다.

## LLM API 호출 실패의 주요 원인

LLM API 호출 실패는 크게 두 가지 범주로 나눌 수 있습니다:

*   **일시적 오류 (Transient Errors)**: 네트워크 문제, 서비스 측의 일시적인 과부하, 서버 재시작 등으로 인해 발생하는 오류입니다. 잠시 후 재시도하면 성공할 가능성이 높습니다. HTTP 429 (Too Many Requests), 500 (Internal Server Error), 503 (Service Unavailable), 504 (Gateway Timeout) 등이 여기에 해당합니다.
*   **영구적 오류 (Permanent Errors)**: 인증 실패 (401 Unauthorized), 잘못된 요청 형식 (400 Bad Request), 존재하지 않는 리소스 (404 Not Found) 등 근본적인 문제로 인해 발생하는 오류입니다. 재시도해도 성공할 가능성이 없거나 매우 낮습니다.

안정적인 시스템 설계를 위해서는 이 두 가지 유형의 오류를 구분하여 적절하게 대응해야 합니다.

## 안정성 확보를 위한 핵심 폴리시

### 1. 타임아웃 (Timeouts) 설정

모든 API 호출에는 적절한 타임아웃을 설정해야 합니다. 무한정 응답을 기다리는 것은 시스템 리소스를 고갈시키고 전체 서비스 지연으로 이어집니다. Connection Timeout과 Read Timeout을 모두 설정하여, 연결 시도와 응답 데이터 수신에 대한 최대 대기 시간을 정의합니다. LLM 호출은 응답이 길어질 수 있으므로, 일반적인 API보다 긴 타임아웃이 필요할 수 있습니다.

### 2. Rate Limiting (속도 제한)

LLM API는 대부분 사용량에 따라 엄격한 Rate Limit을 적용합니다. 이를 초과하면 429 HTTP 상태 코드와 함께 요청이 거부됩니다. 클라이언트 측에서 Rate Limit을 능동적으로 관리하는 것이 중요합니다. API 응답의 `Retry-After` 헤더를 활용하여 다음 요청까지 대기해야 할 시간을 파악하고, 이를 재시도 로직에 반영하는 것이 최신 트렌드입니다. 토큰 버킷(Token Bucket) 또는 리키 버킷(Leaky Bucket) 알고리즘을 사용하여 자체 Rate Limiter를 구현할 수도 있습니다.

### 3. 서킷 브레이커 (Circuit Breaker)

서킷 브레이커 패턴은 서비스의 cascading failures(연쇄 실패)를 방지하는 데 필수적입니다. 특정 API 호출이 연속적으로 실패하거나 오류율이 임계치를 초과할 경우, 서킷을 'Open' 상태로 전환하여 더 이상의 요청을 차단합니다. 일정 시간 후 'Half-Open' 상태로 전환하여 소수의 요청만 허용하고, 성공하면 'Closed' 상태로 복구됩니다. 이는 LLM 서비스가 과부하 상태일 때 추가적인 부하를 줄여 스스로 회복할 시간을 제공합니다.

## 재시도 로직 (Retry Logic) 구현

재시도 로직은 일시적 오류에 대한 회복탄력성을 제공합니다. 효과적인 재시도 로직은 다음과 같은 요소를 포함합니다.

### 1. 지수 백오프 (Exponential Backoff)

실패 시 재시도 간격을 점진적으로 늘리는 전략입니다. 짧은 간격으로 재시도하다가 실패하면 다음 재시도까지 대기하는 시간을 두 배로 늘리는 방식입니다. 이는 LLM 서비스에 대한 부하를 줄이고, 서비스가 회복할 충분한 시간을 줍니다.

### 2. 지터 (Jitter) 적용

순수한 지수 백오프는 많은 클라이언트가 동시에 재시도를 시작하여 또 다른 피크 부하를 유발할 수 있습니다. 이를 방지하기 위해 지터(Jitter)를 적용하여 재시도 간격에 무작위성을 부여합니다. 'Full Jitter'는 백오프 시간 내에서 무작위 값을 선택하는 가장 효과적인 방법 중 하나입니다.

### 3. 최대 재시도 횟수 및 최대 지연 시간

무한 재시도는 피해야 합니다. 최대 재시도 횟수(Max Retries) 또는 총 재시도 시간(Max Delay)을 설정하여, 너무 오래 시도하지 않도록 합니다. 영구적 오류로 판단되면 빠르게 실패하는 것이 중요합니다.

### 4. Idempotency (멱등성) 고려

재시도가 가능한 API 호출은 멱등성을 갖는 것이 이상적입니다. 즉, 동일한 요청을 여러 번 보내도 시스템 상태가 한 번 보낸 것과 동일하게 유지되어야 합니다. LLM API는 일반적으로 요청 본문에 따라 다른 응답을 생성하므로, 요청 자체가 멱등성을 보장하지 않을 수 있습니다. 따라서 요청 전후의 상태를 확인하거나, 클라이언트 측에서 고유한 요청 ID(Request ID)를 생성하여 서버 측에서 중복 요청을 처리할 수 있도록 하는 것이 좋습니다.

## 코드 예제: Python tenacity 라이브러리 활용

Python의 `tenacity` 라이브러리는 유연하고 강력한 재시도 기능을 제공합니다.

```python
import openai
from tenacity import retry, wait_exponential, stop_after_attempt, retry_if_exception_type, wait_random_exponential
import requests

# 재시도 대상 예외 유형 정의
# OpenAI API는 requests.exceptions.HTTPError 대신 자체 예외를 발생시킬 수 있습니다.
# 예를 들어 openai.RateLimitError, openai.APIError 등
RETRY_EXCEPTIONS = (
    openai.RateLimitError,
    openai.APIError,
    requests.exceptions.ConnectionError,
    requests.exceptions.Timeout,
    requests.exceptions.HTTPError
)

# LLM API 호출을 위한 재시도 데코레이터
# 2초에서 최대 60초까지 지수 백오프, 최대 7회 시도, 지터 적용
@retry(
    wait=wait_random_exponential(multiplier=1, min=2, max=60),
    stop=stop_after_attempt(7),
    retry=retry_if_exception_type(RETRY_EXCEPTIONS),
    reraise=True # 모든 재시도 실패 시 마지막 예외를 다시 발생
)
def call_llm_api_with_retry(prompt: str, model: str = "gpt-4o-mini", temperature: float = 0.7) -> str:
    try:
        response = openai.chat.completions.create(
            model=model,
            messages=[
                {"role": "system", "content": "You are a helpful assistant."},
                {"role": "user", "content": prompt}
            ],
            temperature=temperature,
            timeout=30 # API 호출 타임아웃 (초)
        )
        return response.choices[0].message.content
    except requests.exceptions.RequestException as e:
        # requests 관련 예외 처리, 특히 HTTP 상태 코드 확인
        if e.response is not None and e.response.status_code in [400, 401, 403, 404]:
            # 영구적 오류는 재시도하지 않고 바로 실패
            print(f"Permanent error: {e.response.status_code} - {e.response.text}")
            raise
        raise # 일시적 오류는 tenacity가 처리하도록 다시 발생
    except openai.APIStatusError as e:
        if e.status_code in [400, 401, 403, 404]:
            print(f"Permanent OpenAI API error: {e.status_code} - {e.response}")
            raise
        raise

# 사용 예시
if __name__ == "__main__":
    try:
        result = call_llm_api_with_retry("Explain the concept of quantum entanglement in simple terms.")
        print(f"LLM Response: {result[:200]}...")
    except Exception as e:
        print(f"Failed after multiple retries: {e}")
```

### Mermaid 다이어그램: LLM API 호출 흐름과 재시도 로직

```mermaid
sequenceDiagram
    participant Client
    participant CircuitBreaker
    participant LLM_API

    Client->>+CircuitBreaker: LLM Request(Prompt)
    alt Circuit Open
        CircuitBreaker-->>-Client: Fail (Circuit Open)
    else Circuit Half-Open
        CircuitBreaker->>LLM_API: Limited Request(Prompt)
        alt Success
            LLM_API-->>CircuitBreaker: Response
            CircuitBreaker-->>-Client: Success (Circuit Closed)
        else Failure
            LLM_API-->>CircuitBreaker: Error
            CircuitBreaker-->>-Client: Fail (Circuit Open)
        end
    else Circuit Closed
        loop Max Retries
            Client->>+LLM_API: LLM Request(Prompt)
            LLM_API->>LLM_API: Process Request
            alt Success
                LLM_API-->>-Client: LLM Response
                break
            else Rate Limit (429)
                LLM_API-->>-Client: Error (429, Retry-After)
                Client->>Client: Wait(Retry-After + Jitter)
            else Transient Error (5xx)
                LLM_API-->>-Client: Error (5xx)
                Client->>Client: Wait(Exponential Backoff + Jitter)
            else Permanent Error (4xx except 429)
                LLM_API-->>-Client: Error (4xx)
                break loop
            end
        end
        alt All Retries Failed
            Client-->>-Client: Final Failure
        end
    end
```

## 2026년 LLM API 안정성 트렌드 반영

*   **어댑티브 폴리시 (Adaptive Policies)**: 정적(Static)인 재시도 간격이나 Rate Limit 대신, LLM API의 실시간 성능 지표(Latency, Error Rate)를 모니터링하여 동적으로 재시도 전략을 조정하는 시스템이 중요해지고 있습니다. 예를 들어, 특정 모델의 응답 시간이 급증하면 재시도 간격을 자동으로 늘리는 방식입니다.
*   **분산 추적 및 가시성 (Distributed Tracing & Observability)**: LLM API 호출이 복잡한 마이크로서비스 아키텍처를 거치는 경우, 각 구간의 지연 및 오류를 정확히 파악하기 위한 분산 추적(Distributed Tracing)이 필수적입니다. OpenTelemetry와 같은 표준을 사용하여 재시도 횟수, 백오프 시간, 각 단계의 응답 시간 등을 로깅하고 시각화함으로써 문제 진단 시간을 단축할 수 있습니다.
*   **캐스케이딩 폴백 (Cascading Fallbacks)**: 주요 LLM API가 장시간 장애를 겪을 경우, 성능은 낮지만 안정적인 다른 LLM 모델 또는 경량화된 로컬 모델로 자동 전환하는 폴백(Fallback) 전략을 구현하는 것이 일반화되고 있습니다. 이는 서비스의 핵심 기능을 유지하는 데 도움을 줍니다.

## 트레이드오프

### 1. 지연 시간 vs. 안정성 (Latency vs. Reliability)

*   **언제 좋은가**: 재시도 로직은 일시적인 API 오류로부터 복구하여 시스템의 전반적인 안정성을 크게 향상시킵니다. 중요한 비즈니스 로직에 LLM이 사용될 때 필수적입니다.
*   **언제 나쁜가**: 재시도는 필연적으로 전체 응답 시간을 증가시킵니다. 특히 낮은 지연 시간이 critical한 실시간 상호작용 서비스에서는 재시도 간격과 횟수를 신중하게 조절해야 합니다.

### 2. 구현 복잡성 vs. 시스템 견고성 (Implementation Complexity vs. System Robustness)

*   **언제 좋은가**: 서킷 브레이커, 지수 백오프, 지터 등의 고급 폴리시 및 재시도 패턴은 프로덕션 환경에서 발생할 수 있는 다양한 장애 시나리오에 대비하여 시스템을 견고하게 만듭니다. 대규모 분산 시스템에서 연쇄 장애를 방지하는 데 필수적입니다.
*   **언제 나쁜가**: 이러한 패턴들은 초기 구현 및 테스트에 추가적인 복잡성을 수반합니다. 간단한 유틸리티 스크립트나 비핵심 기능의 경우, 과도한 재시도 로직은 불필요한 오버헤드가 될 수 있습니다.

### 3. 리소스 사용량 vs. 오류 전파 방지 (Resource Usage vs. Error Propagation Prevention)

*   **언제 좋은가**: 서킷 브레이커와 클라이언트 측 Rate Limiting은 LLM API 공급자와 클라이언트 서비스 양측의 리소스 과부하를 방지하고, 장애 전파를 효과적으로 차단합니다.
*   **언제 나쁜가**: 잘못된 재시도 설정(예: 과도하게 짧은 백오프, 너무 많은 재시도)은 오히려 LLM API에 불필요한 부하를 가중시켜 문제를 악화시킬 수 있습니다. 또한, 재시도 자체로 인해 클라이언트 측의 메모리 및 CPU 리소스가 추가로 소모됩니다.

## 실전 체크리스트

프로젝트에 LLM API 안정성 폴리시 및 재시도 로직을 적용할 때 다음 항목들을 검증해야 합니다.

*   [ ] 모든 LLM API 호출에 대해 최소한의 Connection Timeout과 Read Timeout이 설정되었는가?
*   [ ] LLM API 응답의 HTTP 상태 코드(특히 429, 5xx)에 따라 지수 백오프와 지터가 적용된 재시도 로직이 구현되었는가?
*   [ ] 재시도 횟수 또는 총 재시도 시간에 대한 합리적인 상한선(Max Retries / Max Delay)이 정의되었는가?
*   [ ] 연속적인 오류 발생 시 LLM API 호출을 일시적으로 중단하는 서킷 브레이커 패턴이 구현되었는가?
*   [ ] LLM API 공급자가 제시하는 Rate Limit을 클라이언트 측에서 능동적으로 준수하는 메커니즘이 있는가 (예: `Retry-After` 헤더 활용)?
*   [ ] 재시도 로직이 적용되는 LLM API 호출이 멱등성을 고려하여 설계되었거나, 중복 요청에 대한 안전 장치(예: 고유 요청 ID)가 마련되었는가?
*   [ ] LLM API 호출의 성공/실패, 재시도 횟수, 응답 시간 등을 포함한 상세한 로깅 및 모니터링 시스템이 구축되었는가?
*   [ ] LLM API 호출 실패 시 사용자에게 적절한 피드백을 제공하거나, 대안(Fallback) 동작이 정의되었는가?
