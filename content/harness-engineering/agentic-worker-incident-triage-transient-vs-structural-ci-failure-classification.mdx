## 문제

허브-워커 병렬 에이전트 생태계에서 허브의 `worker-incident-triage` chain은 워커가 CI 실패를 감지하면 생성하는 이슈를 처리한다. 문제는 **dispatch 시점과 허브 트리아지 시점 사이의 시간 간격**이다.

```
워커 사이클 완료 → CI 실패 감지 → hub-dispatch issue 생성
                                              ↓  (수분~수시간 경과)
허브 사이클 → worker-incident-triage chain → 이슈 읽기
```

허브가 이슈를 처리할 때, 실패의 원인이 이미 사라진 경우(transient)와 여전히 존재하는 경우(structural)를 구별해야 한다.

## 핵심 인사이트: 경과 시간 = 자연 disambiguation 신호

**Transient 실패**는 외부 조건(네트워크 blip, 배포 race, 임시 API 불안정)에 의한 것으로, 원인 코드 변경 없이 자가해소된다. **Structural 실패**는 코드나 설정의 실질적 오류(lockfile drift, missing dependency, broken logic)로, 명시적 수정이 필요하다.

이 두 유형은 dispatch 시점에는 구별하기 어렵다. 하지만 경과 시간 후 트리아지 시점에서는 자연 필터가 작동한다:

```
dispatch → 경과 시간 → 트리아지
    |                       |
 실패 상태               현재 CI 상태
(일시적이거나              (Transient: 이미 PASS)
  구조적)                  (Structural: 여전히 FAIL)
```

**트리아지 시점의 현재 CI 상태가 과거 실패 유형을 소급 분류**한다.

## 분류 알고리즘

```bash
# 트리아지 step 1: 현재 CI 상태 확인
gh run list --repo <worker-repo> --branch main --limit 5

# 현재 PASS → transient였음 → close without code change
# 현재 FAIL → structural → investigate + fix
```

| 현재 CI 상태 | 분류 | 허브 액션 |
|---|---|---|
| ✅ PASS (최근 커밋 기준) | Transient | 이슈 close + "CI now passing, transient" 코멘트 |
| ❌ FAIL (동일 실패 지속) | Structural | `/investigate` → 근본 원인 수정 → PR + close |
| ⚠️ PASS (이후 커밋이 수정) | 이미 자체 수정됨 | 이슈 close + 수정 커밋 참조 |

## Evidence

**Transient 사례 — cycle 934, issue #1032**:
moneyball Vercel deploy 실패 dispatch. 트리아지 시점: 최신 CI ✅ PASS. 결론: Vercel 일시 오류(transient). 코드 변경 없이 close.

**Structural 사례 — cycles 470~480, issues #557~#569**:
pnpm lockfile drift로 moneyball CI 반복 실패 dispatch. 트리아지 시점: 매번 CI ❌ FAIL. 결론: structural. 실제 lockfile sync 수정(cycle 480, commit 55ecd62) 후 해소.

두 사례의 패턴 대비:

| 속성 | Transient (#1032) | Structural (#557-569) |
|---|---|---|
| 이슈 수 | 1건 | 13건 (반복 dispatch) |
| 트리아지 시 CI | ✅ PASS | ❌ FAIL |
| 허브 액션 | close only | investigate + fix |
| 코드 변경 | 없음 | lockfile sync |
| 반복 발생 | 없음 | 수정 전까지 지속 |

## 추가 신호: 반복 dispatch

structural 실패는 수정 전까지 반복 dispatch를 생성한다. transient는 단발 dispatch 후 재발이 없다. 이슈 count가 보조 신호:

```
이슈 1건 → transient 가능성 ↑
이슈 N건 (동일 패턴) → structural 가능성 ↑
```

단, 워커가 같은 transient를 여러 번 잡을 경우 단발이 아닐 수 있으므로 **반드시 현재 CI 상태로 최종 확인**.

## 경계 조건

**false transient (trap)**: CI가 현재 PASS지만 다른 커밋이 수정한 경우. 실제로는 structural이었으나 다른 수정이 우연히 해소. 트리아지 시 수정 커밋 확인 필요:

```bash
git log --oneline -5  # 이슈 생성 이후 커밋에 "fix" 있는지 확인
```

**slow burn structural (trap)**: CI는 PASS지만 silent degradation이 시작된 경우. 이건 현재 CI 상태 휴리스틱 범위 밖 — 별도 `/investigate` 트리거 필요.

## 적용 맥락

이 패턴은 다음 조건을 만족하는 모든 다중 에이전트 시스템에 적용된다:
1. 워커 에이전트가 CI 실패를 허브에 dispatch
2. 허브의 트리아지가 dispatch 후 일정 시간 경과 후 실행
3. CI 파이프라인이 외부 재시도 없이 재실행 결과를 외부에서 확인 가능

**경과 시간이 길수록 transient/structural 자연 필터 효과가 강해진다.** 즉각 트리아지보다 지연 트리아지가 분류 정확도를 오히려 높이는 역설적 특성.
