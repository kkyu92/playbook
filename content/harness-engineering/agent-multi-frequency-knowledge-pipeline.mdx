## 문제

자동화 에이전트가 지식을 생성하는 속도와 그 지식을 처리·승격하는 속도가 일치하지 않는다. 단일 속도로 운영하면 두 가지 실패 모드가 발생한다:

1. **처리 과부하**: 수집 속도 > 처리 속도 → 미처리 인풋 누적, 품질 저하
2. **처리 낭비**: 처리 속도 > 수집 속도 → 빈 큐레이션 사이클, 리소스 낭비

**실측 사례 (2026-05-19)**: worker-lesson auto-ingest 가 약 12회/시간 실행. 허브 develop-cycle 이 하루 N 사이클 실행. 비율이 수십 배 차이나지만 시스템은 정상 작동 중 — 각 단계가 서로 다른 주파수로 비동기 운영되기 때문.

## 4-계층 주파수 모델

자동화 지식 파이프라인은 처리 목적에 따라 4개의 주파수 계층으로 분리된다.

### 계층 1 — 원시 수집 (Raw Capture) · 고주파

```
빈도: 분 단위 (12회/시간 예시)
형태: worker → lesson commit → auto-ingest workflow
역할: 모든 에이전트 관찰을 손실 없이 저장
품질 기준: 없음 (필터링 X)
```

에이전트가 생성한 모든 lesson 을 원시 상태로 보존. 이 단계에서 필터링하면 signal 이 소실될 수 있다. 고속 · 무선택 · append-only.

### 계층 2 — 주기적 큐레이션 (Periodic Curation) · 중주파

```
빈도: 시간 단위 / 사이클 단위 (N회/일)
형태: hub develop-cycle → curate chain → lint + learn
역할: 원시 수집에서 패턴 추출, orphan/stale 정리, 메모리 갱신
품질 기준: "2회 이상 재발 패턴"
```

1회성 관찰은 journal 에 머문다. 2회+ 재발하면 wiki 후보로 격상. 이 계층이 "신호 vs 노이즈" 분류의 실질적 경계.

### 계층 3 — 위키 엔트리 생성 (Wiki Entry Creation) · 저주파

```
빈도: 일 단위 (수 회/주)
형태: explore-idea chain → office-hours → 구현 → commit
역할: 검증된 패턴을 구조화된 지식 엔트리로 변환
품질 기준: "신규 통찰 + 검색 가능성 + connections ≥ 1"
```

JIT search 선행으로 중복 생성 방지. 이미 유사 entry 가 있으면 생성 skip — 이 계층에서의 낭비가 wiki 무덤의 주원인.

### 계층 4 — 솔루션 승격 (Solution Promotion) · 극저주파

```
빈도: 주 단위 / 월 단위
형태: scan-promotions.mjs → _compiled-truth.md → command/hook/lib
역할: 반복 검증된 솔루션을 자동화 코드로 승격
품질 기준: "카테고리 내 3건 이상 + 반복 검증"
```

가장 희소하고 가장 고품질. 승격된 솔루션은 future agent 의 default 행동을 바꾼다.

## 주파수 간 비율 (2026-05-19 실측)

```
계층 1 (raw capture):    ~12회/시간 = ~288회/일
계층 2 (curation):       ~8회/일 (develop-cycle hub N=8)
계층 3 (wiki entry):     ~1회/일 (explore-idea 사이클 시)
계층 4 (promotion):      ~1회/주 (3건 누적 시)

비율 (1→2→3→4):
  288 : 8 : 1 : 0.14 ≈ 2000 : 56 : 7 : 1
```

각 계층은 아래 계층보다 약 7~8배 더 느리게 처리한다. 이 비율이 "정보 밀도 증폭기" 역할을 한다 — 위로 올라갈수록 품질이 높아진다.

## 설계 원칙

### 원칙 1: 계층 간 버퍼

각 계층 사이에 버퍼(queue)가 있어야 한다. 이 시스템에서 버퍼는:
- 1→2 버퍼: git repository (origin/main auto-ingest commits)
- 2→3 버퍼: journal entries + cycle_state.json retro
- 3→4 버퍼: docs/solutions/ 디렉토리

버퍼 없이 직결하면 계층 간 속도 차이가 블로킹을 유발한다.

### 원칙 2: 비동기 폴링

상위 계층은 하위 계층을 블로킹하지 않는다. 큐레이션 사이클이 언제 시작되는지 raw capture 는 알 필요 없다. 폴링 기반 — 큐레이션 시점에 "지금까지 쌓인 것 처리" 모델.

### 원칙 3: 상향 필터, 하향 불가

아래에서 위로만 승격한다. 위키 엔트리가 journal 로 강등되지 않는다. 각 계층은 previous 계층의 output 중 일부만 선택한다.

### 원칙 4: 주파수 독립성

각 계층의 주파수는 서로 독립적으로 조정 가능하다. worker-lesson 이 24회/시간으로 2배 빠르게 실행되어도 큐레이션 주파수는 변경 불필요. 버퍼가 흡수한다.

## 적용 조건

**적합한 경우:**
- 에이전트가 지속적으로 관찰을 생성하는 시스템 (자동화 루프 상시 실행)
- 지식의 "발견 시점" 과 "활용 최적 시점" 이 다른 경우
- 여러 속도의 에이전트(워커 N개 + 허브 1개)가 공존하는 구조

**부적합한 경우:**
- 단발성 에이전트 실행 (1회만 실행하는 task)
- 실시간 지식 활용이 필요한 경우 (low-latency 요구사항)
- 에이전트 수가 적어 수집 주파수 자체가 낮은 경우

## 안티패턴

### 안티패턴 1: 단일 주파수 강제

모든 계층을 같은 속도로 운영하려는 시도. 예: "raw capture 할 때마다 즉시 wiki entry 생성". 결과: wiki entry 품질 저하 + 큐레이션 부담 폭증.

### 안티패턴 2: 상위 계층 과부하

큐레이션(계층 2)을 raw capture(계층 1) 속도에 맞추려는 시도. 12회/시간 원시 수집에 대응해 develop-cycle 도 12회/시간 실행하면 token 비용이 기하급수 증가. 버퍼 없이 처리 강제 = 계층 구조 붕괴.

### 안티패턴 3: 버퍼 우회

"너무 쌓였다" 는 이유로 버퍼를 비우거나 무시. 미처리 journal 이 많다고 일괄 삭제하면 아직 패턴으로 부상하지 않은 signal 이 소실된다.

## 실측 건강 지표

```bash
# 계층 1 주파수 측정 (최근 1시간 auto-ingest 횟수)
gh run list --workflow=auto-ingest.yml --limit 20 --json createdAt \
  | python3 -c "
import json, sys, datetime
data = json.load(sys.stdin)
now = datetime.datetime.utcnow()
one_hour_ago = now - datetime.timedelta(hours=1)
recent = [r for r in data if datetime.datetime.fromisoformat(r['createdAt'].replace('Z','+00:00')).replace(tzinfo=None) > one_hour_ago]
print(f'Layer 1 frequency: {len(recent)} runs/hour')
"

# 계층 2 주파수 측정 (오늘 hub develop-cycle 횟수)
ls ~/.develop-cycle-hub/cycles/*.json 2>/dev/null | while read f; do
  python3 -c "import json; d=json.load(open('$f')); print(d.get('started_at','')[:10])" 2>/dev/null
done | grep "$(date +%Y-%m-%d)" | wc -l
```

**정상 비율**: 계층 1:2 ≥ 10:1. 비율이 2:1 미만이면 큐레이션이 과도하게 실행 중 — 불필요한 curation 사이클 발생.
