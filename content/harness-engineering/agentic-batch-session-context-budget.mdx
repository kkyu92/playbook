## 문제

Manual batch 세션에서 각 사이클은 컨텍스트를 생산/소비한다:

- **생산**: git log, gh issue list, lint 결과, JIT search 결과, 작성한 entry 내용
- **소비**: 이전 사이클 결과가 컨텍스트에 잔류

20 사이클 기준 컨텍스트 구성:
- 사이클 1: skill 로딩 (~5K tokens) + 진단 결과
- 사이클 10: 이전 9 사이클 결과 누적
- 사이클 20: 이전 19 사이클 결과 누적 → 컨텍스트 경계 도달 가능

## 증상

- 후반 사이클에서 진단 요약이 짧아짐 (컨텍스트 압축 발생)
- 초반 사이클의 세부 내용이 "압축"으로 대체됨
- 복잡한 entry 작성 시 품질 저하

## 완화 전략

### 전략 1 — Lean 진단 (스캔 결과 최소화)

```bash
# 후반 사이클에서는 핵심만
git rev-list --left-right --count origin/main...main 2>/dev/null  # 1줄
gh issue list --limit 3  # 3줄 max
# git log --oneline -20 → git log --oneline -5
```

### 전략 2 — Entry 내용 외부 박제

entry 전체를 컨텍스트에 쓰지 말고 파일로만 쓰기. 컨텍스트에는 "entry 작성됨: #N slug" 1줄만 유지.

### 전략 3 — cycle_state JSON 요약화

후반 사이클 cycle_state JSON write 시 핵심 필드만:
- cycle_n, chain_selected, outcome, next_recommended_chain
- results 세부 skip (git history에 있음)

### 전략 4 — N 임계값 분할

N=20 단일 세션보다 N=10 × 2 세션이 후반 품질 유지에 유리. 하이브리드: 처음 10 사이클은 explore-idea 집중, 다음 10 사이클은 새 세션에서 curate/review.

## 실전 관찰

cycle 992~1011 (20 사이클 batch):
- 사이클 1~10: 진단 풀 스캔 + 상세 entry 작성
- 사이클 11~20: lean 진단 + 간결 entry (자연 적응)
- 컨텍스트 압축 발생하더라도 git history + cycle_state JSON으로 recovery 가능 → 치명적 아님
