## 문제

wiki entry 수가 늘어나도 소비가 없으면 무덤이다. 표면 지표가 속인다:

- **lint CLEAN** → orphan 0 / stale 0 → "건강해 보임"
- **entry 수 증가** → 201개 → "성장하고 있음"

하지만 실제로 LLM 이 그 entry 를 사용했는지는 알 수 없다. 생산만 있고 소비 메커니즘이 없으면 wiki 는 노드 더미가 된다.

**소비 메커니즘 = JIT search.** `pnpm search "<쿼리>" 3 --inject` 호출이 유일한 소비 채널이다. 이 채널의 데이터가 `data/search-hits.json` 에 누적된다.

## 3축 측정

### 축 1 — 검색 사용률 (Search Usage Rate)

```
사용률 = totalQueries / 기간(사이클 수)
```

`data/search-hits.json` → `totalQueries` 필드로 직접 측정.

- **baseline (2026-05-19)**: 181 queries / ~800 cycles = **0.23 queries/cycle**
- **목표**: JIT search 선행 4-chain (explore-idea / curate / fix-incident / worker-incident-triage) 충실 이행 시 사이클당 0.5+ queries
- **경고**: 사이클당 0.1 이하 = search 사실상 미사용. wiki 는 생산 전용 모드.

### 축 2 — 히트율 (Hit Rate)

```
히트율 = search-hits.json entries 수 / total wiki entries 수
```

search-hits.json 의 `hits` 객체에 포함된 entry slug 수 = "한 번이라도 결과에 반환된 entry".

- **baseline (2026-05-19)**: 84 / 201 = **42%**
- **의미**: 58% (117 entries) 는 아직 어떤 query 에서도 매칭된 적 없음.
- **경고**: 히트율 30% 미만 → 대부분 entry 가 사실상 invisible. embedding 품질 또는 실제 사용 빈도 문제.

### 축 3 — 결정 변경률 (Decision Change Rate)

```
결정 변경률 = search 결과가 행동을 바꾼 사이클 수 / search 호출 사이클 수
```

직접 측정 불가 (LLM 내부 추론). 간접 proxy:
- **중복 생성 skip**: search 결과로 "이미 있음" 발견 → 신규 entry 생성 안 함
- **기존 solution 재활용**: fix-incident chain 에서 기존 solution 찾아 재구현 skip
- **curate carry-over 변경**: 무덤 후보 판단 변경

evidence 는 cycle_state.json 또는 retro summary 에 "search 결과 → chain 행동 변경" 명시로 추적.

- **baseline**: 명시적 tracking 없음 → 0%로 간주 (undercount 높음)
- **목표**: N=10 사이클 내 결정 변경 ≥ 1회 명시 기록

## 실측 데이터 (2026-05-19 기준)

```
totalQueries: 181
tracked entries (hit ≥ 1): 84 / 201 (42%)

Top 5 most searched:
  reports/closed-loop-health                 14 hits

  infrastructure/github-actions-billing-...  5 hits
  journal/playbook-journal-012-...            4 hits
  harness-engineering/guard-test-pattern      4 hits
```

**관찰**:
1. `closed-loop-health` 가 압도적 1위 (14/181 = 7.7% 단독 점유). 대시보드 용도로 반복 참조됨.
2. harness-engineering / journal / retro 가 상위 — 허브 자체 운영 패턴이 가장 자주 검색됨.
3. 157개 queries 의 target entry 는 long tail 분산.

## 무덤 진단 기준 (3축 복합)

| 상태 | 진단 기준 | 대응 |
|---|---|---|
| 무덤 위험 | 사이클당 search 0.1 이하 + 히트율 30% 미만 | JIT search 4-chain 선행 강화 |
| 생산 과잉 | entry 수 증가율 > search rate 증가율 | curate chain 으로 stale 정리 우선 |
| 소비 과잉 | 같은 entry 반복 hit 5+ 회 | 해당 entry confidence 상향 + connections 보강 |
| 건강 | 사이클당 0.3+, 히트율 40%+, 결정 변경 분기당 1+ | 현행 유지 |

## 측정 자동화

```bash
# 검색 사용률 + 히트율 즉시 확인
python3 -c "
import json
d = json.load(open('data/search-hits.json'))
total = d.get('totalQueries', 0)
hits = len(d.get('hits', {}))
entries = $(ls content/**/*.mdx 2>/dev/null | wc -l | tr -d ' ')
print(f'totalQueries: {total}')
print(f'hit rate: {hits}/{entries} = {hits*100//entries}%')
"
```

## 개선 방향

1. **JIT search 4-chain 선행 강화**: explore-idea / curate / fix-incident / worker-incident-triage 매번 search 선행. 사이클당 0.5+ queries 목표.
2. **결정 변경률 명시 tracking**: cycle_state.json 에 `search_decision_changes: []` 필드 추가 → 행동 변경 사례 list 박제.
3. **hit-rate 분기별 측정**: 3개월마다 히트율 측정 → 지속 40% 미만이면 entry embedding 재검토.
4. **0-hit entry 리뷰**: 히트 0회 entry 가 6개월 이상 유지되면 curate → stale 판정 후보.
