자율 에이전트(develop-cycle)가 빠르게 회전할수록, 매 사이클 자동 push는 CI/CD 배포 할당량을 빠르게 소진한다. Vercel 무료 플랜의 100 배포/일 한도는 이 문제의 대표적 사례다. 24 사이클 세션에서 매 사이클 push + CI 실행 + Vercel 배포 = 48+ 배포 소진. 세션 2개면 할당량이 바닥난다.

**핵심 통찰**: LLM 에이전트의 commit은 git history에 즉시 박제되지만, push는 CI를 트리거하고 배포를 유발한다. 이 두 단계를 분리하면 에이전트 자율성을 유지하면서 배포 할당량을 보존할 수 있다.

## 패턴: 3계층 commit 분류

### 1. Deploy-free commit (자율 영역)

CI를 트리거하지 않거나 트리거해도 배포가 불필요한 commit. 에이전트가 자유롭게 박제.

| commit prefix | 내용 | 배포 필요성 |
|---|---|---|
| `policy:` | cycle-retro, meta-pattern, chain-evolution | ❌ |
| `memory:` | 메모리 갱신, 자가 학습 | ❌ |
| `lesson:` | 학습 박제 | ❌ |
| `content:` | 위키 엔트리 (MDX) | ❌ (빌드 검증만) |
| `data:` | 자동 ingest 원천 데이터 | ❌ |

### 2. 배포 필요 commit (배치 영역)

기능 변경, 스크립트 수정, 워크플로 변경 등 실제 배포가 필요한 commit. 로컬에서 누적한 후 사용자 명시 시점에 일괄 push.

| commit prefix | 내용 | 배포 필요성 |
|---|---|---|
| `feat:` | 신규 기능 | ✅ |
| `fix:` | 버그 수정 | ✅ |
| `refactor:` | 코드 구조 변경 | ✅ (변경 검증) |

### 3. push 트리거 조건 (사용자 결정 영역)

에이전트가 자율적으로 push하지 않는다. 다음 조건에서만 push:

- 사용자 명시 ("push 해" / "deploy 해" / "ship batch")
- 사이클 N 회전 종료 시점 (사용자가 인지)
- 에이전트가 `/ship` skill을 통해 사용자 확인 후 진행

## ROI 계산

```
시나리오 A (매 사이클 자동 push):
24 사이클 × 2 events/push (CI + Vercel) = 48 배포 소진

시나리오 B (배치 push):
N 사이클 → 1 push = 2 배포 소진

절감 = 48 - 2 = 46 배포 절감 (96% 절감)
하루 한도 100회 → 시나리오 A = 2.08 세션 후 한도 도달
              → 시나리오 B = 50 세션 가능
```

## 설계 원칙

### commit ≠ push 분리

에이전트 입장에서 commit은 "작업 완료 박제"고, push는 "외부 시스템에 공개"다. 이 두 단계의 의미를 다르게 취급하면:

- commit: 로컬 git history = 에이전트 자율 영역 (무한 가능)
- push: 외부 CI/CD 트리거 = 할당량 소비 (제한적 자원)

### zero-touch 모드에서 자율 push 금지

1세션 1사이클 zero-touch 회전에서 watch.sh가 매 사이클마다 새 세션을 자동으로 시작한다. 이 환경에서 자율 push를 허용하면:

1. 에이전트가 push를 판단 → CI 자동 트리거
2. Vercel deploy 자동 발생
3. N 사이클 후 할당량 고갈 → 다음 세션 배포 실패
4. 에이전트가 배포 실패를 incident으로 진단 → fix 시도 → 더 많은 push

**피드백 루프 위험**: 자율 push → 배포 실패 → fix push → 더 많은 배포 실패. 한도 차단 환경에서 자가 증폭.

### 허브-워커 분리 정합

워커(moneyball, blog-autopilot)는 자체 CI/CD 한도를 가진 별도 repo다. 허브가 워커 대신 push를 트리거하지 않는다. 각 시스템이 자기 push 정책을 독립적으로 관리.

## 실전 패턴: deploy-free commit 누적

```bash
# zero-touch 회전 중 에이전트의 일반적 작업 시퀀스
git add content/harness-engineering/new-entry.mdx
git commit -m "content: 신규 entry #256 agentic-ci-deploy-budget-batch-push-policy"
# push X — 로컬 누적

git add -p scripts/some-fix.ts
git commit -m "fix: some bug fix"
# push X — 로컬 누적

# cycle-retro dispatch
git commit --allow-empty -m "policy: cycle 949 retro..."
# push X — 로컬 누적

# ... N 사이클 후 사용자 "push 해"
git push origin main  # 이 시점 한 번만 CI/CD 트리거
```

N 사이클의 작업이 1회 CI/CD run으로 검증된다.

## 일반화: 어떤 할당량에도 적용

Vercel 배포 한도는 대표 사례일 뿐이다. 동일 패턴이 적용되는 다른 할당량:

| 제약 | 자원 | 배치 단위 |
|---|---|---|
| GitHub Actions 분 (무료 2000분/월) | CI 실행 시간 | 여러 commit 묶어 1 push |
| API rate limit (Gemini, OpenAI) | API 호출 수 | 배치 처리 |
| Vercel deploy (100/일) | 배포 횟수 | 사이클 N 후 1 push |
| GitHub API rate limit (5000/시) | API 호출 | 캐싱 + 배치 |

**공통 원칙**: 자원 소비 연산을 에이전트 로컬 작업과 분리하고, 소비는 사용자 인지 시점에 배치 실행.

## 안티패턴: 배포 오판

에이전트가 "기능 변경이 있으므로 즉시 push해야 한다"고 판단하는 경향. 이 판단은:

1. 실제 배포 긴급성을 과대평가 (대부분의 위키 엔트리, 스크립트 변경은 몇 시간 지연이 문제없음)
2. 할당량 소비를 과소평가 (매 사이클 push = 하루 한도 빠른 소진)
3. 사용자 컨트롤을 침해 (언제 배포할지는 사용자 결정)

올바른 판단 기준: "지금 당장 배포하지 않으면 시스템이 중단되는가?" → 거의 항상 No.

## 검증 evidence

- 허브 발화 900+ 사이클 (2026-05-21 기준)
- zero-touch 24 사이클 세션에서 push 0회 자율 수행
- 메모리 `feedback_deploy_strategy`: "Vercel 일 100회 제한, push는 묶어서 사용자 요청 시만"
- cycle 당 평균 2~4 commit, push는 사용자 명시 시점만 (배치 크기: 평균 150~270 commit)
