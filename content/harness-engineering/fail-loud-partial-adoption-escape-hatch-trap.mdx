## 문제

fail-loud 패턴 (`assertSelectOk`, `assertWriteOk`, throw-on-error 헬퍼) 을 파일에 도입했지만 **기존 try/catch 블록을 제거하지 않으면**:

```
cycle 143: assertSelectOk 도입 ✅
cycle 143: daily.ts line 370-378 기존 try/catch 미제거 ← 이 시점에 놓침
cycle 143~211: 4 사이클 동안 해당 경로는 fail-loud 보호 없이 운영
```

도입 PR이 green 이어도 **파일 일부 경로는 여전히 old pattern** 으로 작동.

## 패턴 구조

### 부분 적용 하이브리드 (안티패턴)

```typescript
// ✅ 새 경로: assertSelectOk 로 fail-loud
const predictions = assertSelectOk(
  await supabase.from('predictions').select('*').eq('date', date),
  'predictions'
);

// ❌ 오래된 경로: try/catch 가 남아서 에러 삼킴
try {
  const { data, error } = await supabase
    .from('pipeline_runs')
    .insert({ ... });
  if (error) return; // ← 조용히 return, assertWriteOk 미적용
} catch (e) {
  // ← catch 가 에러 삼킴
}
```

두 경로가 같은 파일에 공존 → 코드 리뷰어가 "이미 assertSelectOk 사용 중" 으로 오인.

## 왜 놓치는가

| 이유 | 설명 |
|---|---|
| **도입 PR 범위 제한** | 새 패턴 도입 PR 은 "도입 증명" 에 집중. 기존 코드 전수 교체는 별도 PR 로 분리 → 교체 PR 누락 |
| **CI 통과** | 하이브리드 상태도 테스트 통과 — 기존 try/catch 경로가 예외를 잡아서 실패를 숨김 |
| **리뷰 맹점** | 리뷰어가 "이 파일은 assertSelectOk 사용한다" 로 기억 → 나머지 경로 스캔 생략 |
| **파일 크기** | 1000줄+ 파일에서 기존 try/catch 위치는 수백 줄 떨어진 곳에 있을 수 있음 |

## 해결 패턴

### 도입 PR 체크리스트

```bash
# 신규 패턴 도입 직후 파일 전체 scan
grep -n "try {" daily.ts | wc -l          # 남은 try/catch 건수
grep -n "if (error) return" daily.ts      # null/error 무시 경로
grep -n "\.catch(" daily.ts              # promise catch 체인
grep -n "assertSelectOk\|assertWriteOk" daily.ts | wc -l  # 새 패턴 건수

# "새 패턴 건수 < 전체 DB 쿼리 건수" 이면 부분 적용 상태
grep -n "supabase\." daily.ts | wc -l
```

### Finish pass (전수 교체)

신규 패턴 도입 PR 이후 **별도 "finish pass" PR**:

```
PR 1: assertSelectOk 도입 (신규 경로)
PR 2: finish pass — 기존 try/catch + null fallback 전수 교체
```

PR 2 없이 PR 1 만 머지하면 하이브리드 상태 확정.

## 실 사례 (moneyball daily.ts, cycle 143→211)

```
cycle 143: assertSelectOk 도입 (daily.ts 여러 경로 적용)
cycle 143: line 370-378 try/catch gap 미발견 → 방치
cycle 211: daily.ts 1182줄 전체 read → gap 발견
           "finish() 우회 → pipeline_runs 미기록" 구조 수정
           4 사이클 (68 cycle?) 동안 pipeline_runs 기록 누락 가능성
```

**차이**: cycle 143 PR review = 신규 경로 확인만 (패턴 도입 증명). cycle 211 = 파일 전수 read → 기존 escape hatch 발견.

## 운영 가이드라인

```
□ 신규 fail-loud 패턴 도입 시 파일 전수 scan 필수
□ grep "try {\|\.catch(" <파일> 실행해서 잔존 escape hatch 건수 확인
□ 잔존 건수 > 0 이면 "finish pass" PR 별도 계획
□ 대형 파일 (500+ 줄) 은 도입 PR 와 finish pass PR 분리
□ review-code chain: "assertSelectOk 사용 중" = 전체 적용 보장 X
```
