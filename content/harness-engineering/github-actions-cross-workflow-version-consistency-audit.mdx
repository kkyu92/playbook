워크플로 파일에서 action version을 변경하기 전에 **같은 repo의 다른 워크플로가 동일 action을 어떤 버전으로 사용하는지 먼저 확인**해야 한다. 이미 성공적으로 실행 중인 워크플로가 있다면 해당 버전은 유효하다.

## 사례 — cycle 1350 (2026-07-06)

`incident-auto-close.yml` 픽스 시 `actions/checkout@v5`를 `@v4`로 변경:

```yaml
# 변경 전 (원래 코드)
uses: actions/checkout@v5

# 변경 후 (불필요한 변경)
uses: actions/checkout@v4
```

**이유**: AI(학습 컷오프 Aug 2025)가 `@v4`를 최신 버전으로 알고 있어 `@v5`가 존재하지 않는다고 판단.

**실제**: repo의 17개 워크플로 모두 `actions/checkout@v5` 사용 중, 모두 성공적으로 실행됨. v5는 2025년 이후 릴리즈된 유효한 버전.

실제 원인은 `@v5` 버전이 아니라 PYEOF heredoc column-0 문제였다.

## 진단 명령어

픽스 전 버전 현황 체크:
```bash
# 특정 action 버전 전체 현황
grep -r "actions/checkout@" .github/workflows/ | sort | uniq

# 모든 action 버전 현황
grep -rhE "uses: [a-z-]+/[a-z-]+@" .github/workflows/ | sort | uniq

# 해당 버전이 실제로 작동하는지 확인 (다른 workflow 실행 이력)
gh run list --workflow=<other-workflow-using-same-version> --limit 5
```

## AI 학습 컷오프와 action version 신뢰도

| 상황 | 신뢰도 |
|---|---|
| 같은 repo 다른 workflow가 해당 버전 사용 + 성공 | 높음 — 변경 불필요 |
| 해당 버전을 사용하는 다른 workflow 없음 | 낮음 — 실제 확인 필요 |
| AI가 "버전 없음" 권장 | 중간 — repo 현황과 교차 검증 필수 |
| AI 학습 컷오프 이후 릴리즈된 버전 | 학습 데이터 부재 — repo 현황 우선 |

**원칙**: repo에서 이미 성공적으로 실행 중인 버전은 AI가 알지 못해도 유효하다.

## 올바른 워크플로 픽스 순서

1. **문제 재현 확인** — 실제 실패 원인 찾기
2. **cross-workflow audit** — 유사 패턴이 다른 workflow에 있는지 확인
3. **버전 일관성 확인** — 변경할 버전이 다른 workflow에서 사용 중인지 확인
4. **최소 변경 원칙** — 실제 원인만 변경, 불필요한 변경 금지
5. **PR description에 감사 결과 포함** — "다른 17개 workflow 모두 @v5 사용, 이번 변경은 필수 아님"

## 버전 일관성 유지 이점

- 다른 workflow에서 버전 문제 발생 시 빠른 탐지
- repo 전체 action 버전 표준화 → 업그레이드 시 일괄 처리
- "이 버전은 작동하나요?" 불확실성 제거

## 관련 패턴

- **AI 학습 컷오프 보정**: repo 현황이 AI 지식보다 정확할 때는 repo 우선
- **BRANCHED local fix quality**: local에서 검증 안 된 변경도 유사한 신뢰도 이슈
- **최소 변경 원칙**: "의심스러우면 건드리지 않는다"
