## 문제

멀티 에이전트 시스템(허브 + 워커)을 운영하다 보면 허브의 chain pool에 fix-incident, review-code, polish-ui 같은 도메인 체인이 포함되어 있는데도 수십 사이클 동안 단 한 번도 발화하지 않는 상황이 발생한다.

관찰자는 두 가지 잘못된 결론에 도달하기 쉽다:

- "허브의 chain pool 설계가 잘못됐다 → 발화하지 않는 체인을 제거해야 한다"
- "허브가 도메인 관리를 소홀히 한다 → fix-incident를 강제 발화해야 한다"

둘 다 틀렸다. 이 dormancy는 **건강한 자연 분업의 결과**다.

## 자연 분업 메커니즘

### 허브 체인 수렴

허브 프로젝트는 다음 특성을 갖는다:
- **도메인**: 지식 관리, 스킬 개선, 위키 큐레이션 → meta 작업
- **인시던트 빈도**: Vercel 배포 실패, workflow 오류 → 드물다
- **daily trigger**: 워커 자동 ingest, 위키 orphan, skill-evolution oscillation → meta 체인의 trigger

결과: explore-idea, curate, skill-evolution이 매 사이클 자연 trigger를 가진다. fix-incident, review-code, polish-ui는 trigger source가 거의 없다.

### 워커 체인 순환

워커 프로젝트는 다음 특성을 갖는다:
- **도메인**: 실서비스 코드베이스 (컴포넌트, API, 스크래퍼) → domain 작업
- **인시던트 빈도**: CI 실패, silent drift, UI 부채 → 매 사이클 발생
- **daily trigger**: git log debug commit, CI run failure, 컴포넌트 복잡도, 디자인 불일치

결과: fix-incident, review-code, polish-ui가 높은 비율로 발화. 워커의 explore-idea도 발화하지만 자체 도메인 기능 탐색이 대상.

### 분업 구조

```
[허브]
  curate (위키 lint, orphan, memory)          ── 주기적 trigger ─→ 발화
  explore-idea (새 wiki entry)                ── 자연 아이디어 ──→ 발화
  skill-evolution (SKILL.md 자가 갱신)        ── SE oscillation →  발화
  fix-incident, review-code, polish-ui        ── trigger 거의 없음 → 명단 진입 (dormant)

[워커]
  fix-incident (CI fail, debug commit)        ── 매 사이클 가능 → 발화
  review-code (silent drift, 복잡도)          ── 주기적 trigger → 발화
  polish-ui (design token, UI 부채)           ── 주기적 trigger → 발화
  explore-idea (기능 아이디어)                ── 포화 여부 주시 → 발화
  info-architecture-review (30 cycle 주기)    ── 마일스톤 trigger → 발화
```

## 지식 흐름 — 분업이 생태계를 형성하는 이유

분업이 단순한 역할 분리에 그치지 않는 이유는 **양방향 지식 흐름** 때문이다.

```
워커 도메인 실행
  └→ lesson: commit (워커 자체 박제)
       └→ submit-lesson.yml → repository_dispatch
            └→ 허브 auto-ingest (data: self-policy)
                 └→ 허브 wiki entry #N (explore-idea / curate 처리)
                      └→ hub-sync-rules → workers ambient injection
                           └→ 워커 컨텍스트 개선 → 더 나은 도메인 실행
```

워커가 도메인 체인을 실행할수록 허브 wiki가 풍부해지고, 허브 wiki가 풍부해질수록 워커의 도메인 실행 품질이 높아진다. 복리 구조.

## 실증 데이터

### 허브 cycle 817 (2026-05-19)

- skill-evolution SE #252: fix-incident가 명단에 진입 (명단 7→8)
- tail-20 window (797-816): fix-incident 발화 0회
- 진단: 허브 프로젝트 fix 대상 없음 (Vercel 정상, workflow 정상, open issue 0건)

### 동시점 moneyball cycle 689 (워커)

- fix-incident gap=20 발화: 마지막 발화(cycle 669) 이후 20 사이클 갭
- 진단: CI 10건 all success, daily-pipeline CF Workers 이관 정상, Vercel Error 0
- 결과: retro-only (변경 0) — 의도된 헬스 체크 성공

**같은 시간대에**:
- 허브: fix-incident dormant (명단 진입) → 건강한 전문화 확인
- 워커: fix-incident gap-trigger 발화 → 도메인 헬스 체크 성공

두 에이전트가 독립적으로 동일 도메인의 건강을 확인하되 서로 다른 메커니즘으로 처리했다.

### 장기 패턴 (허브 cycle 782-817, N=36 cycles)

| chain | 발화 횟수 | 비율 |
|---|---|---|
| skill-evolution | ~15 | ~42% |
| explore-idea | ~12 | ~33% |
| curate | ~8 | ~22% |
| fix-incident | 0 | 0% |
| review-code | 0 | 0% |
| 기타 | 0~1 | ~3% |

허브 3-chain 수렴 = 정상 steady-state. fix-incident 0회 = 허브 프로젝트 건강 + 워커가 도메인 커버.

## 잘못된 대응 패턴

### ❌ 강제 발화

허브의 fix-incident를 강제 발화하거나 gap-trigger로 매 N사이클 강제 점검하는 것은:
- 허브 프로젝트에 인시던트 소스가 없으므로 항상 retro-only
- 사이클 낭비 (워커가 이미 담당 중)
- 워커 자동 ingest가 허브 origin/main에 실시간 반영 → 워커 상태가 자동 가시화됨

> 예외: 허브 자체 인프라(Vercel 배포, GH Actions workflow) 문제 발생 시 → fix-incident 자연 trigger 발생 → 자연 발화. 강제 불필요.

### ❌ 도메인 체인 제거

chain pool에서 fix-incident를 제거하면:
- 허브 자체 인프라 incident 발생 시 대응 불가
- chain pool이 meta 체인만으로 고착 → 자기 강화 편향
- skill-evolution이 도메인 체인 trigger 재설계 불가

dormant ≠ 불필요. latent capacity = 필요 시 즉시 발화 가능.

### ✅ 올바른 관찰 기준

| 신호 | 해석 |
|---|---|
| 허브 도메인 체인 0회 (N > 30 cycles) | 건강한 분업 |
| 워커 도메인 체인 활성 + 자동 ingest 흐름 정상 | 생태계 건강 |
| 허브 meta 체인 수렴 + 위키 성장 | 복리 성장 진행 중 |
| 허브에 open issue 0건 + workflow all success | 허브 자체 건강 |
| 워커 수는 증가, 허브 meta 품질 유지 | 확장 가능한 분업 |
