## 패턴

R6 TODOS 항목의 잔류 기간에 따른 분류:

| 잔류 기간 | 분류 | hub 대응 |
|---|---|---|
| 0-20 사이클 (~1주) | 미해결 (pending) | 매 사이클 우선도 유지, 사용자 가시화 |
| 20-100 사이클 (~1개월) | 처리 대기 | 사이클 mid-review 시 상태 갱신 |
| 100+ 사이클 (수개월) | 수용된 제약 (accepted) | 배경 상태로 전환, 압박 없이 추적 |

## BRANCHED 상태 사례

```
[P0] R6 push — playbook hub local fix origin 미반영
  첫 등록: cycle 1120 (2026-05-27 경)
  현재: cycle 1399 (2026-07-08)
  잔류: ~279 사이클, ~6주
  분류: 수용된 제약
```

279 사이클 동안 BRANCHED 상태가 지속됐지만:
- 워커 auto-ingest (4-6건/일) + 허브 cycle commits (1-2/cycle) = 구조적 양방향 발산
- 사용자 주도 머지 시점에 자연 해소 → 즉시 재발 (4 cycle 주기)
- hub가 강제 해소 불가 (force-push = R6)

**결론**: BRANCHED 는 버그가 아닌 **양방향 병렬 성장의 구조적 결과**. 수용된 제약.

## 수용된 제약 vs 미해결의 판별 기준

| 판별 기준 | 미해결 | 수용된 제약 |
|---|---|---|
| 자율 처리 가능성 | 허브가 commit + CI로 해결 가능 | 반드시 사용자 개입 필요 (R6) |
| 재발 구조 | 1회 fix → 완전 해소 | fix 직후 재발 (구조적) |
| 비즈니스 영향 | 기능 차단 또는 데이터 오류 | 불편함 (정기 해소 시점까지) |
| 잔류 기간 증가 시 | 누적 리스크 증가 | 리스크 불변 (구조 동일) |

## TODOS 갱신 정책

수용된 제약으로 분류된 항목:
1. **주기적 상태 갱신**: 매 20-30 사이클마다 현재 수치만 갱신 (BRANCHED local X / origin Y)
2. **압박 제거**: "긴급", "ASAP" 문구 제거
3. **근거 명시**: "재발 구조" 한 줄 추가 → 다음 세션 컨텍스트 즉시 파악
4. **DONE으로 이동 금지**: 수용됐지만 아직 해소되지 않은 항목은 활성 유지

항목 삭제 기준: 해당 기능/서비스가 사용 중단되거나 사용자가 명시적으로 "더 이상 관리 불필요"라고 지시한 경우에만.

## 주기적 갱신 의무

중요한 점: 수용됐어도 **수치 갱신은 의무**. 오래된 수치 (BRANCHED local 100 / origin 20 이 여전히 기재되어 있으면) 다음 세션에서 잘못된 판단 유발. cycle 내 갱신이 발생하면 실제 수치로 교체.
