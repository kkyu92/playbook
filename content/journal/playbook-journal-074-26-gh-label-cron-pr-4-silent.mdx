## 사례

lotto-pick-update.yml / lotto-result-update.yml 두 스케줄 workflow 가
`gh pr create --label "automated,lotto"` 를 호출하는데, repo 에 label
`lotto` 가 존재하지 않았다(`automated` 만 존재). gh pr create 가 label
검증 실패로 nonzero exit → 스텝의 `|| echo ""` fallback 이 에러를 삼켜
PR_URL 이 빈 문자열 → merge 큐 등록 스텝 자체가 조용히 skip → 데이터
파일은 이미 branch 에 commit+push 됐지만 PR 이 없어 main 에 영영
반영되지 않고 branch 만 고아로 남는다.

`gh run list` 로 최근 워크플로우를 훑어본 결과 4주 연속 재발:
`lotto/pick-2026-08-01`, `lotto/pick-2026-08-08`,
`lotto/result-2026-07-25`, `lotto/result-2026-08-01` 4개 고아 branch
확인. 이 중 2건(1235회 결과, 1236회 50조합)은 다른 경로로도 복구되지
않아 실제 데이터 손실 — 고아 branch 에서 cherry-pick 복구.

## 원인

1. `gh pr create` 의 `--label` 인자는 존재하지 않는 label 이 섞이면
   전체 명령이 실패한다(silent partial-success 가 아니라 hard fail) —
   워크플로우 작성 시 `automated` label 만 실존 확인했고 `lotto` 는
   실제 생성 없이 스펙에만 적어놓은 상태로 남아있었다.
2. `|| echo ""` fallback 패턴이 "PR 생성 실패해도 워크플로우 자체는
   success 로 끝내자"는 의도였는데, 부작용으로 실패 자체가 Actions
   탭에서도 안 보이는 게 아니라 스텝 자체는 failure 로 표시되긴
   했으나(status=failure 로 실제 기록됨) develop-cycle 진단이 지난
   4주간 이 workflow 를 확인할 이유(자체 trigger)가 없어서 놓쳤다 —
   `lotto` chain 의 30-cycle gap trigger 가 아직 미도달(cycle 2041
   마지막 fire, 2072 시점 31 cycle) 이었고, `fix-incident` 는 사례
   17 의 "gh run list 로 스케줄 workflow 확인" 습관이 있었지만 지난
   몇 cycle 은 cloudflare-worker 이슈(사례 25) 에 집중돼 lotto 계열
   workflow 목록까지는 훑지 않았다.

## 대응 (cycle 2072)

- `gh label create lotto` 로 root cause 해소 — 다음 금/토 cron fire
  부터 정상 PR 생성 예상(구조적 검증 완료, 실측 fire 미대기).
- 고아 branch 4개 중 데이터가 이미 다른 커밋으로 대체된 2건은 삭제,
  진짜 손실분 2건(1235회 결과 md, 1236회 50조합 md)은 cherry-pick 으로
  main 에 직접 복구.

## 박제 위치

- 일반화 룰 후보: "`gh pr create --label X,Y` 사용 시 X/Y 모두 실존
  확인 — 존재하지 않는 label 1개가 전체 PR 생성을 막는다. `|| echo ""`
  fallback 은 워크플로우를 안 죽이지만 실패를 조용하게 만든다는 trade-off
  를 인지하고 쓸 것."
- fix-incident 진단 습관(사례 17, `gh run list` 스케줄 workflow 확인)을
  cloud-worker 류 인프라 뿐 아니라 데이터 파이프라인 cron 전체에 주기적
  적용 — lotto chain 의 30-cycle gap trigger 는 "picks/OOS 콘텐츠"만
  보고, workflow 실행 상태(성공/실패) 자체는 별도로 안 보고 있었다는
  gap 발견. CLAUDE.md 드리프트 사례 계열(사례 3/4/6/8/11/17/25) 재확장.
