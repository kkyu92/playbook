LLM(Large Language Model)의 출력은 종종 사용자 친화적인 소통 방식 때문에 실제 정보의 엄밀성과 정확성이 희생될 수 있습니다. `sol-astrizer` 방법론은 이러한 LLM의 경향을 제어하고, 분석적이고 객관적인 결과물을 일관되게 생성하도록 유도하는 체계적인 접근 방식입니다.

## `sol-astrizer` 방법론의 필요성
초기 LLM 모델, 예를 들어 Claude Opus 5.5나 Gemini Neon과 같은 모델들은 버그 해결 여부를 물었을 때 성급하게 "네"라고 확답하거나, 사용자의 불만을 먼저 공감하려다 사실 관계를 혼동하는 경향이 있었습니다. 이러한 과잉 친절, 근거 없는 확답, 서로 다른 개념의 혼재는 LLM이 코드 작성, 버그 진단, 시스템 분석 등 기술적으로 엄밀한 작업에 활용될 때 심각한 문제로 이어질 수 있습니다. `sol-astrizer`는 가상의 "GPT 6.2"와 같이 차분하고 분석적인 엄밀함을 어떤 LLM이나 코딩 에이전트에게도 적용하여, 신뢰할 수 있는 출력을 보장하는 것을 목표로 합니다.

## 핵심 원칙
`sol-astrizer` 방법론은 다음의 핵심 원칙을 기반으로 LLM의 출력을 정제합니다.

1.  **사실 기반 분리 (Fact-Based Deconstruction)**: 복잡한 질문이나 문제 상황을 검증 가능한 개별적인 사실들로 분해하고, 각 사실에 대한 증거를 명확히 요구합니다.
2.  **개념 독립성 유지 (Concept Isolation)**: 밀접하게 관련되어 있어도 엄연히 다른 개념들을 한데 섞지 않고 명확히 구분하여 설명합니다.
3.  **증거 기반 확답 (Evidence-Backed Assertions)**: 어떤 주장이나 결론을 내릴 때는 반드시 명확한 근거나 증거를 제시하도록 요구하며, 증거가 불충분할 경우 불확실성을 명시하고 추가 검증 절차를 제안합니다.
4.  **객관적이고 중립적인 태도 (Objective & Neutral Tone)**: 감정적인 표현, 과도한 공감, 불필요하게 친절한 언어를 지양하고, 오직 사실과 분석에 기반한 중립적인 어조를 유지합니다.

## `sol-astrizer` 통합 전략

`sol-astrizer` 방법론은 크게 두 가지 영역에서 LLM 워크플로우에 통합될 수 있습니다.

### 1. 프롬프트 엔지니어링 통합 (Prompt Engineering Integration)

*   **시스템 프롬프트 명시화**: LLM의 시스템 프롬프트에 `sol-astrizer`의 핵심 원칙들을 명시적으로 포함시켜, LLM이 모든 응답에 대해 이러한 기준을 따르도록 지시합니다.
*   **부정적 제약 (Negative Constraints)**: "절대로 단정하지 마라", "불필요한 공감 표현을 삼가라", "개념을 혼동하지 마라"와 같이 LLM이 피해야 할 행동을 명확히 지시합니다.
*   **구조화된 출력 요구 (Structured Output Requirements)**: LLM이 JSON, YAML 등 특정 구조화된 포맷으로 응답하도록 요구하여, 각 정보의 종류(사실, 가정, 결론, 검증 단계)를 명확히 분리하고 파싱을 용이하게 합니다.
*   **단계별 추론 지시 (Step-by-Step Reasoning)**: `Chain-of-Thought`나 `Self-Correction`과 같은 기법을 활용하여, LLM이 최종 답변 전에 충분한 분석과 추론 과정을 거치도록 유도합니다.

### 2. 출력 검증 파이프라인 적용 (Output Validation Pipeline Application)

*   **의미론적 검증 (Semantic Verification)**: LLM이 제시한 개념들이 실제 의미론적으로 정확하게 분리되어 있는지 검증하는 로직을 구현합니다.
*   **주장 검증 (Assertion Falsification)**: LLM의 주장이 제공된 컨텍스트나 외부 도구의 결과(예: 코드 컴파일 결과, API 응답)에 의해 뒷받침되는지 자동으로 확인합니다.
*   **어조 분석 (Tone Analysis)**: 출력 텍스트의 어조를 분석하여 과도한 친절함이나 불필요한 단정적인 표현이 포함되어 있는지 감지하고 경고합니다.
*   **외부 도구 의존성 명시 (Explicit Tool Dependency)**: LLM이 스스로의 답변 검증을 위해 특정 외부 도구(예: 코드 린터, 데이터베이스 쿼리)가 필요하다고 명시하도록 요구하고, 해당 도구의 실행을 워크플로우에 통합합니다.
